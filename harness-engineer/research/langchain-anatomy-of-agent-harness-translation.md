# Agent Harness 的解剖（中文翻译）

**来源**: https://blog.langchain.com/the-anatomy-of-an-agent-harness/  
**作者**: Vivek Trivedy  
**日期**: March 10, 2026

---

**TLDR:** Agent = Model + Harness。Harness 工程是我们如何在模型周围构建系统以将它们转化为工作引擎的方法。模型包含智能，而 Harness 使该智能变得有用。我们定义了什么是 Harness，并推导出今天和明天的 Agent 所需的核心组件。

---

## 有人能定义一下 "Harness" 吗？

Agent = Model + Harness

**如果你不是模型，你就是 Harness。**

Harness 是每一段代码、配置和执行逻辑，除了模型本身。原始模型不是 Agent。但当 Harness 赋予它状态、工具执行、反馈循环和可执行约束等功能时，它就变成了 Agent。

具体而言，Harness 包括以下内容：

- 系统提示词
- 工具、技能、MCP 及其描述
- 捆绑的基础设施（文件系统、沙箱、浏览器）
- 编排逻辑（子 Agent 生成、交接、模型路由）
- 确定性执行的钩子/中间件（压缩、继续、lint 检查）

在模型和 Harness 之间划分 Agent 系统的边界有很多混乱的方式。但在我看来，这是最干净的定义，因为它迫使我们思考**围绕模型智能设计系统。**

本文的其余部分将介绍核心 Harness 组件，并从模型的核心原语出发，推导*为什么*每个部分存在。

## 为什么我们需要 Harness…从模型的角度来看

**有些事情我们希望 Agent 做，但模型无法开箱即用。这就是 Harness 的用武之地。**

模型（主要）接收文本、图像、音频、视频等数据，并输出文本。仅此而已。开箱即用，它们无法：

- 在交互之间保持持久状态
- 执行代码
- 访问实时知识
- 设置环境并安装包以完成工作

这些都是 **Harness 级别的功能**。LLM 的结构需要某种包装它们的机制来完成有用的工作。

例如，要获得像"聊天"这样的产品 UX，我们将模型包装在一个 while 循环中，以跟踪以前的消息并追加新的用户消息。阅读本文的每个人都已使用过这种 Harness。主要思想是，我们希望将期望的 Agent 行为转换为 Harness 中的实际功能。

---

## 从期望的 Agent 行为逆向推导 Harness 工程

Harness 工程帮助人类注入有用的先验知识来引导 Agent 行为。随着模型变得越来越强大，Harness 被用来手术式地扩展和纠正模型，以完成以前不可能的任务。

我们不会列出每个 Harness 功能的详尽清单。目标是从帮助模型做有用工作的起点推导出一组功能。我们将遵循以下模式：

**我们想要的行为（或想要修复的）→ 帮助模型实现这一点的 Harness 设计。**

![](https://blog.langchain.com/content/images/2026/03/image-1.png)

## 用于持久存储和上下文管理的文件系统

**我们希望 Agent 拥有持久存储，以便与真实数据交互、卸载不适合上下文的信息，并在会话之间持久化工作。**

模型只能直接操作其上下文窗口内的知识。在文件系统之前，用户必须将内容直接复制/粘贴到模型，那是笨拙的 UX，对自主 Agent 不起作用。世界已经在使用文件系统来完成工作，因此模型自然接受了数十亿个关于如何使用它们的 token 训练。自然的解决方案变成了：

**Harness 提供文件系统抽象和文件操作工具。**

文件系统可以说是最基础的 Harness 原语，因为它解锁了以下内容：

- Agent 获得一个工作空间来读取数据、代码和文档。
- 工作可以增量添加和卸载，而不是将所有内容保存在上下文中。Agent 可以存储中间输出并维护超越单个会话的状态。
- **文件系统是自然的协作表面。** 多个 Agent 和人类可以通过共享文件进行协调。像 Agent 团队这样的架构依赖于此。

Git 为文件系统添加了版本控制，因此 Agent 可以跟踪工作、回滚错误和分支实验。我们在下面更多地回顾文件系统，因为它证明是其他我们需要的关键 Harness 原语。

---

## Bash + 代码作为通用工具

**我们希望 Agent 自主解决问题，而无需人类预先设计每个工具。**

今天的主要 Agent 执行模式是 [ReAct 循环](https://docs.langchain.com/oss/python/langchain/agents)，模型推理、通过工具调用采取行动、观察结果，并在 while 循环中重复。但 Harness 只能执行它们有逻辑的工具。与其强迫用户为每个可能的操作构建工具，更好的解决方案是给 Agent 一个像 bash 这样的通用工具。

**Harness 提供 bash 工具，因此模型可以通过编写和执行代码自主解决问题。**

Bash + 代码执行是向**给模型一台计算机**并让它们自主解决其余问题迈出的一大步。模型可以通过代码动态设计自己的工具，而不是受限于固定的预配置工具集。

Harness 仍然提供其他工具，但代码执行已成为自主问题解决的默认通用策略。

---

## 用于执行和验证工作的沙箱和工具

**Agent 需要一个具有正确默认设置的环境，以便它们可以安全地行动、观察结果并取得进展。**

我们已经给了模型存储和执行代码的能力，但所有这一切都需要在某个地方发生。本地运行 Agent 生成的代码是有风险的，单个本地环境无法扩展到大型 Agent 工作负载。

**沙箱为 Agent 提供安全的操作环境。** Harness 可以连接到沙箱来运行代码、检查文件、安装依赖项和完成任务，而不是在本地执行。这创建了代码的安全、隔离执行。为了更安全，Harness 可以允许列表命令并强制执行网络隔离。沙箱还解锁了规模，因为环境可以按需创建，分散到许多任务中，并在工作完成后拆除。

**好的环境带有好的默认工具。** Harness 负责配置工具，以便 Agent 可以做有用的工作。这包括预安装语言运行时和包、用于 git 和测试的 CLI、用于 Web 交互和验证的[浏览器](https://github.com/vercel-labs/agent-browser)。

浏览器、日志、截图和测试运行器等工具为 Agent 提供了一种观察和分析其工作的方式。这帮助它们创建**自验证循环**，它们可以在其中**编写应用程序代码、**运行测试、检查日志并修复错误。

模型不会开箱即用地配置自己的执行环境。决定 Agent 在哪里运行、有哪些工具可用、它可以访问什么，以及如何验证其工作，都是 Harness 级别的设计决策。

## 用于持续学习的记忆和搜索

**Agent 应该记住它们看到的内容，并访问训练时并不存在的信息。**

模型除了其权重和当前上下文中的内容外，没有额外的知识。在没有访问编辑模型权重的情况下，"添加知识"的唯一方式是通过**上下文注入。**

对于记忆，文件系统再次成为核心原语。Harness 支持记忆文件标准，如 [AGENTS.md](http://agents.md/)，这些文件在 Agent 启动时注入到上下文中。当 Agent 添加和编辑此文件时，Harness 将更新的文件加载到上下文中。这是一种[持续学习](https://www.ibm.com/think/topics/continual-learning)的形式，Agent 在一个会话中持久存储知识，并将该知识注入到未来的会话中。

知识截止意味着，如果没有用户直接提供，模型无法直接访问新数据，如更新的库版本。对于最新的知识，网络搜索和 MCP 工具如 [Context7](https://context7.com/) 帮助 Agent 访问知识截止之外的信息，如训练停止时不存在的新库版本或当前数据。

网络搜索和用于查询最新上下文的工具是 Harness 中值得内置的有用原语。

## 对抗上下文腐烂

**Agent 性能不应随着工作进程而下降。**

[Context Rot](https://research.trychroma.com/context-rot) 描述了随着上下文窗口填满，模型在推理和完成任务方面变得更糟的情况。上下文是一种宝贵且稀缺的资源，因此 Harness 需要管理它的策略。

**今天的 Harness 很大程度上是良好上下文工程的传递机制。**

**压缩（Compaction）** 解决了当上下文窗口接近填满时该怎么办的问题。没有压缩，当对话超过上下文窗口时会发生什么？一个选项是 API 报错，那不好。Harness 必须对这种情况使用某种策略。因此，压缩智能地卸载和总结现有的上下文窗口，以便 Agent 可以继续工作。

**工具调用卸载** 有助于减少大型工具输出的影响，这些输出可能会嘈杂地混乱上下文窗口而不提供有用的信息。Harness 保留超过阈值 token 数的工具输出的头部和尾部 token，并将完整输出卸载到文件系统，以便模型可以在需要时访问它。

**技能（Skills）** 解决了在 Agent 启动时将太多工具或 MCP 服务器加载到上下文中从而在 Agent 开始工作之前降低性能的问题。技能是一个 Harness 级别的原语，通过**渐进式披露**解决这个问题。模型没有选择在启动时将 Skill 前言加载到上下文中，但 Harness 可以支持这一点来保护模型免受上下文腐烂。

## 长时程自主执行

**我们希望 Agent 自主、正确地在长时间范围内完成复杂工作。**

自主软件创建是编码 Agent 的圣杯。但今天的模型存在提前停止、分解复杂问题的问题，以及随着工作跨越多个上下文窗口而出现的不连贯性。一个好的 Harness 必须围绕所有这些问题进行设计。

这就是早期的 Harness 原语开始复合的地方。长时程工作需要持久状态、规划、观察和验证，以在多个上下文窗口中保持工作。

**用于跨会话跟踪工作的文件系统和 git。** Agent 在长任务中产生数百万个 token，因此文件系统持久捕获工作以跟踪随时间的进展。添加 git 允许新 Agent 快速了解项目的最新工作和历史。对于多个 Agent 一起工作，文件系统还充当工作的共享账本，Agent 可以在其中协作。

**用于继续工作的 Ralph 循环。** [Ralph Loop](https://ghuntley.com/loop/) 是一种 Harness 模式，通过钩子拦截模型的退出尝试，并在干净的上下文窗口中重新注入原始提示词，迫使 Agent 针对完成目标继续其工作。文件系统使这成为可能，因为每次迭代都以全新的上下文开始，但从前一次迭代读取状态。

**用于保持正轨的规划和自验证。** 规划是模型将目标分解为一系列步骤的时候。Harness 通过良好的提示词和注入如何使用文件系统中的计划文件的提醒来支持这一点。在完成每个步骤后，Agent 通过**自验证**受益于检查其工作的正确性。Harness 中的钩子可以运行预定义的测试套件，并在失败时循环回到模型并显示错误消息，或者可以提示模型独立自评估其代码。验证将解决方案建立在测试中，并创建自我改进的反馈信号。

# Harness 的未来

## 模型训练与 Harness 设计的耦合

今天的 Agent 产品如 Claude Code 和 Codex 都是在循环中使用模型和 Harness 进行后训练的。这有助于模型改进 Harness 设计者认为它们应该天生擅长的动作，如文件系统操作、bash 执行、规划或使用子 Agent 并行化工作。

这创建了一个反馈循环。发现有用的原语，添加到 Harness 中，然后用于训练下一代模型。随着这个循环的重复，模型在它们被训练的 Harness 中变得更加强大。

但这种共同进化对泛化有有趣的副作用。它表现为改变工具逻辑会导致模型性能下降。一个很好的例子在 [Codex-5.3 提示词指南](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide/#apply_patch)中描述了用于编辑文件的 apply_patch 工具逻辑。一个真正智能的模型在切换补丁方法时应该几乎没有困难，但在循环中使用 Harness 进行训练会产生这种过拟合。

**但这并不意味着最适合你任务的 Harness 是模型被后训练的那个。** [Terminal Bench 2.0 排行榜](https://www.tbench.ai/leaderboard/terminal-bench/2.0)是一个很好的例子。Claude Code 中的 Opus 4.6 得分远低于其他 Harness 中的 Opus 4.6。在[之前的博客](https://x.com/Vtrivedy10/status/2023805578561060992?s=20)中，我们展示了仅通过改变 Harness，我们如何将编码 Agent 从 Terminal Bench 2.0 的前 30 名提升到前 5 名。优化适合你任务的 Harness 还有很多潜力可以挖掘。

## Harness 工程的发展方向

随着模型变得越来越强大，今天 Harness 中的一些内容将被吸收到模型中。模型将在规划、自验证和长时程连贯性方面天生变得更好，因此需要更少的上下文注入。

这表明 Harness 应该随着时间的推移变得不那么重要。但就像提示词工程今天仍然有价值一样，Harness 工程很可能继续对构建好的 Agent 有用。

确实，今天的 Harness 弥补了模型的不足，但它们也围绕模型智能工程系统以使其更有效。配置良好的环境、正确的工具、持久状态和验证循环使任何模型都更有效，无论其基础智能如何。

Harness 工程是一个非常活跃的研究领域，我们在 LangChain 使用它来改进我们的 Harness 构建库 [deepagents](https://docs.langchain.com/oss/python/deepagents/overview)。以下是我们今天正在探索的一些开放和有趣的问题：

- 在共享代码库上并行工作的数百个 Agent 的编排
- 分析自己轨迹以识别和修复 Harness 级别故障模式的 Agent
- 为给定任务动态组装正确工具和上下文的 Harness，而不是预先配置的

这篇博客是一个定义什么是 Harness 以及它如何受到我们希望模型做的工作的影响的练习。

**模型包含智能，而 Harness 是使该智能有用的系统。**

致更多的 Harness 构建、更好的系统和更好的 Agent。
