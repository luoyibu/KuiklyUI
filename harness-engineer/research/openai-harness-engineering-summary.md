## 一、核心实验成果

### 1.1 实验背景
- **时间**: 2025年8月 - 2026年2月（5个月）
- **团队**: 3人 → 7人
- **成果**: 
  - 100万行代码
  - 1500个 Pull Request
  - 平均每人每天 3.5 个 PR
  - **关键限制**: 没有一行代码是人工编写的，全部由 Codex 生成
  - **效率提升**: 只用了手工编写代码所需约 1/10 的时间

### 1.2 核心理念
> **人类掌舵。智能体执行。**

工程师的主要工作不再是编写代码，而是：
- 设计环境
- 明确意图
- 构建反馈回路

## 二、关键经验教训

### 2.1 重新定义工程师角色

**传统工程师**: 编写代码  
**Harness 工程师**: 
- 深度优先工作方式
- 将大目标拆解为小构建模块
- 追问："还需要什么能力？如何让能力对智能体清晰可读？"

**工作方式**:
1. 工程师描述任务
2. 运行智能体
3. 智能体打开 Pull Request
4. 智能体自我审核 + 其他智能体审核
5. 循环直到通过

### 2.2 AGENTS.md 不是百科全书，而是地图 ⭐⭐⭐

**失败尝试**: 大型 AGENTS.md（1000页说明书方式）
- ❌ 情境是稀缺资源，大文件会挤掉任务和代码
- ❌ 过多指导反而无效（当一切都"重要"，一切都不重要）
- ❌ 立即腐烂（变成陈旧规则的坟场）
- ❌ 难以核实（不适合机械检查）

**正确做法**: 渐进式披露
```
AGENTS.md (约100行) → 内容目录
├── ARCHITECTURE.md (架构地图)
└── docs/
    ├── design-docs/ (设计文档)
    ├── exec-plans/ (执行计划)
    │   ├── active/
    │   ├── completed/
    │   └── tech-debt-tracker.md
    ├── generated/ (自动生成)
    ├── product-specs/ (产品规范)
    └── references/ (参考资料)
```

**关键原则**:
- 给智能体一张地图，而不是一本说明书
- 结构化知识库作为记录系统
- 专职 linter 和 CI 作业验证知识库
- "doc-gardening" 智能体定期扫描过时文档

### 2.3 目标是智能体的可读性 ⭐⭐⭐

**核心洞察**: 
> Codex 在运行时无法访问的内容 = 不存在

**不可见的知识**:
- Google Docs
- Slack 消息
- 人类头脑中的隐性知识

**解决方案**: 将所有知识编码到代码库中（Markdown 形式）

**为 Codex 提供情境的方式**:
- 组织和展示正确信息
- 像引导新员工一样提供产品原则、工程规范、团队文化
- 选择智能体可以内化推理的依赖项和抽象

### 2.4 规范架构与品味

**架构原则**:
- 强制执行不变量，而非微观管理实施
- 严格边界和可预测结构
- 分层领域架构（Types → Config → Repo → Service → Runtime → UI）

**实践方法**:
- 自定义 linter（由 Codex 生成）
- 结构测试机械强制执行
- 错误信息中注入修复指令
- 中央层面强制执行边界，本地层面允许自主权

**品味反馈循环**:
- 审查评论 → 文档更新或工具编码
- 规则转化为代码

### 2.5 吞吐量改变合并理念

**传统做法**:
- 严格的合并门
- 长时间 PR 生命周期
- 测试失败必须解决

**Harness 做法**:
- 尽量减少阻塞合并门
- PR 生命周期短
- 测试偶发失败通过重跑解决
- **原因**: 纠错成本低，等待成本高

### 2.6 不断提高的自主水平

Codex 现在可以端到端驱动新功能：
1. 验证代码库状态
2. 重现 Bug
3. 录制故障视频
4. 实施修复
5. 验证修复（运行应用）
6. 录制解决方案视频
7. 打开 Pull Request
8. 回应反馈
9. 检测并修复构建故障
10. 仅在需要判断时交由人工处理
11. 合并更改

### 2.7 熵与垃圾收集 ⭐⭐

**问题**: Codex 会复现代码库中已存在的模式（包括不均衡的模式）→ 漂移

**早期做法**: 每周五 20% 时间清理 "AI 残渣"（不可扩展）

**解决方案**: 黄金原则 + 循环清理流程
- 编码主观意见的机械规则
- 后台 Codex 任务扫描偏差
- 更新质量等级
- 发起重构 PR

**类比**: 垃圾回收机制
- 技术债务 = 高息贷款
- 持续小额偿还 > 累积后一次性解决

## 三、关键技术实践

### 3.1 提高应用程序可读性

**瓶颈**: 人工 QA 能力（人类时间和注意力固定）

**解决方案**: 让应用对 Codex 直接可读

**具体措施**:
1. **Git Worktree 启动** - 每次更改启动独立实例
2. **Chrome DevTools 协议** - DOM 快照、截图、导航
3. **可观测性堆栈** - 日志、指标、追踪
   - LogQL 查询日志
   - PromQL 查询指标
   - 完全独立的临时环境

### 3.2 智能体审核循环（Ralph Wiggum 循环）

```
工程师描述任务
    ↓
运行智能体
    ↓
打开 Pull Request
    ↓
Codex 本地自审核
    ↓
请求特定智能体审查
    ↓
响应反馈
    ↓
循环直到通过
    ↓
合并
```

## 四、对 KuiklyUI 的启示

### 4.1 立即可应用的

1. **AGENTS.md 地图化**
   - 保持简短（100行左右）
   - 指向结构化知识库
   - 渐进式披露

2. **知识库结构化**
   - docs/ 作为记录系统
   - 设计文档编目和索引
   - 执行计划版本控制

3. **智能体可读性优先**
   - 代码库内记录所有知识
   - 选择智能体友好的依赖
   - 可检查、可验证、可修改

### 4.2 需要适配的

1. **多工具兼容性**（Claude Code、OpenCode、Cursor、CodeBuddy）
   - 不同工具的情境窗口不同
   - 需要统一的 AGENTS.md 格式
   - 工具特定的优化

2. **Kotlin/KMP 生态**
   - 与 TypeScript/JavaScript 不同
   - 需要特定的 linter 和架构检查
   - 跨平台复杂性

3. **团队规模**
   - OpenAI 实验是 3-7 人小团队
   - KuiklyUI 是开源项目，贡献者更多
   - 需要不同的协作模式

### 4.3 关键成功因素

1. **纪律在支撑结构，而非代码**
2. **工具、抽象、反馈回路的重要性**
3. **持续投资环境设计**
4. **人类判断力的编码**
