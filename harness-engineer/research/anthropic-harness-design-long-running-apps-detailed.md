## 一、文章概述

### 1.1 研究背景

作者在过去几个月致力于解决两个相互关联的问题：
1. 让 Claude 生成高质量的前端设计
2. 让 Claude 无需人工干预构建完整应用

这项工作源于早期的两个项目：
- **前端设计技能** (frontend-design skill)
- **长运行编码 Agent Harness** (long-running coding agent harness)

通过提示工程和 Harness 设计，团队已经将 Claude 的性能提升到基线以上，但两者都遇到了天花板。

### 1.2 核心突破

为了突破瓶颈，作者寻找跨两个截然不同领域（主观品味 vs 可验证正确性）都适用的新型 AI 工程方法。受 **生成对抗网络 (GANs)** 启发，设计了**生成器-评估器双 Agent 架构**。

关键洞察：
- 构建一个可靠且具备"品味"的评估器，需要先将主观判断（"这个设计好吗？"）转化为具体、可评分的标准
- 将这些技术应用于长运行自主编码，延续了之前 Harness 工作的两个教训：
  1. 将构建分解为可处理的块
  2. 使用结构化产物在会话间传递上下文

最终成果：**三 Agent 架构**（规划器、生成器、评估器），能够在多小时内自主编码生成丰富的全栈应用。

## 二、为什么朴素实现会失败

### 2.1 早期实验回顾

在之前的长运行 Harness 实验中：
- 使用**初始化器 Agent** 将产品规范分解为任务列表
- 使用**编码 Agent** 逐个实现功能
- 通过产物在会话间传递上下文

开发者社区也得出类似结论，如 "Ralph Wiggum" 方法使用钩子或脚本让 Agent 保持连续迭代。

### 2.2 两个常见失败模式

#### 失败模式 1：上下文窗口问题

**现象**：
- 模型在长时间任务中随着上下文窗口填满而失去连贯性
- 部分模型表现出"**上下文焦虑**"（context anxiety）：接近自认为的上下文限制时提前结束工作

**解决方案：上下文重置 (Context Reset)**
- 完全清空上下文窗口，启动全新 Agent
- 结合结构化交接，携带前一个 Agent 的状态和下一步计划
- 与"压缩"（Compaction）不同：压缩是在原地总结早期对话，让同一 Agent 继续；重置提供干净起点

**关键发现**：
- Claude Sonnet 4.5 表现出强烈的上下文焦虑，仅靠压缩不足以支持长任务性能
- 上下文重置成为 Harness 设计的核心
- 代价：增加了编排复杂度、token 开销和延迟

#### 失败模式 2：自我评估问题

**现象**：
- Agent 评估自己产出的工作时，倾向于自信地称赞——即使质量明显一般
- 在主观任务（如设计）中尤为严重，没有二进制检查等价于可验证的软件测试
- 即使在有可验证结果的任务中，Agent 有时也会表现出影响任务完成的糟糕判断

**解决方案：分离工作与评估**
- 将执行工作的 Agent 与评判工作的 Agent 分离
- 单独的评估器调校为怀疑论者，比让生成器批评自己的工作更可行
- 一旦存在外部反馈，生成器就有具体的东西可以迭代改进

## 三、前端设计：让主观质量可评分

### 3.1 实验动机

作者首先在前端设计上实验，因为自我评估问题在这里最明显。未经干预时，Claude 倾向于安全、可预测的布局——技术上功能正常但视觉上平淡无奇。

### 3.2 Harness 设计的两个洞察

**洞察 1**：美学无法完全简化为分数，个人品味总有差异，但可以通过编码设计原则和偏好的评分标准来改善。"这个设计美吗？"难以一致回答，但"这是否遵循了我们的好设计原则？"给了 Claude 具体可评分的东西。

**洞察 2**：通过将前端生成与前端评分分离，可以创建反馈循环，推动生成器产生更强的输出。

### 3.3 四项评分标准

作者编写了四项评分标准，同时给生成器和评估器：

| 标准 | 定义 | 重点 |
|------|------|------|
| **设计质量** | 设计是否感觉是一个连贯的整体，而非零件拼凑？色彩、字体、布局、图像等细节是否结合创造了独特的氛围和身份？ | 创意 |
| **原创性** | 是否有定制化决策的证据，还是模板布局、库默认设置和 AI 生成模式？人类设计师应该能识别出有意的创意选择。未修改的库存组件或 AI 生成痕迹（如白卡上的紫色渐变）在此失败。 | 差异化 |
| **工艺** | 技术执行：字体层次、间距一致性、色彩和谐、对比度比例。这是能力检查而非创意检查。大多数合理实现默认就能通过；失败意味着基础 broken。 | 技术 |
| **功能性** | 独立于美学的可用性。用户能否理解界面做什么、找到主要操作、无需猜测即可完成任务？ | 可用性 |

**权重分配**：设计质量和原创性 > 工艺和功能性
- Claude 默认在工艺和功能性上得分良好（所需技术能力对模型来说很自然）
- 但在设计和原创性上，Claude 经常产出平庸的输出
- 标准明确惩罚高度通用的"AI slop"模式
- 通过加权推动模型承担更大的美学风险

### 3.4 评估器调校

使用**少样本示例**（few-shot examples）和详细分数分解来校准评估器，确保：
- 评估器的判断与作者偏好一致
- 减少迭代间的分数漂移

### 3.5 实现架构

基于 **Claude Agent SDK** 构建循环：

1. **生成器 Agent**：根据用户提示创建 HTML/CSS/JS 前端
2. **评估器**：获得 Playwright MCP，可直接与实时页面交互
   - 导航页面、截图、仔细研究实现
   - 按四个标准评分并撰写详细批评
3. **反馈循环**：评估结果流回生成器作为下一次迭代的输入

**迭代策略**：
- 每代运行 5-15 次迭代
- 每次迭代通常推动生成器朝着更独特的方向发展
- 生成器在每个评估后做战略决策：
  - 如果分数趋势良好，细化当前方向
  - 如果方法无效，转向完全不同的美学

**时间成本**：
- 每次迭代需要实际墙钟时间（评估器主动导航页面而非评分静态截图）
- 完整运行可长达**四小时**

### 3.6 实验结果

**分数趋势**：
- 评估器的评估在迭代中改善，然后趋于平稳，仍有提升空间
- 有些代际是渐进细化，有些在迭代间发生剧烈美学转变

**提示词影响**：
- 标准中的措辞以作者未完全预料的方式引导生成器
- 包含"最好的设计是博物馆级别"等短语推动设计向特定视觉趋同
- 表明与标准相关的提示词直接塑造了输出特征

**迭代质量**：
- 分数通常随迭代改善，但并非总是线性
- 后期实现整体更好，但作者经常更喜欢中间迭代而非最后一个
- 实现复杂度往往随轮次增加，生成器响应评估器反馈而追求更雄心勃勃的解决方案

**显著案例**：荷兰艺术博物馆网站
- 第 9 次迭代：干净、深色主题的虚构博物馆落地页，视觉上精致但符合作者预期
- 第 10 次迭代：完全放弃之前方法，重新想象为空间体验：
  - CSS 透视渲染的 3D 房间，棋盘地板
  - 艺术品以自由形式位置挂在墙上
  - 基于门口的画廊房间导航，而非滚动或点击
- 这是单次生成从未见过的创意飞跃

## 四、扩展到全栈编码

### 4.1 应用 GAN 启发模式

将这些发现应用于全栈开发，生成器-评估器循环自然映射到软件开发生命周期，代码审查和 QA 在此扮演与设计评估器相同的结构角色。

### 4.2 架构演进

#### 早期 Harness（Sonnet 4.5 时代）

- **初始化器 Agent**：分解产品规范
- **编码 Agent**：逐个功能实现
- **上下文重置**：会话间关键
- 原因：Sonnet 4.5 表现出强烈的"上下文焦虑"

#### 新架构（三 Agent 系统）

**模型升级**：Opus 4.5 → Opus 4.6
- Opus 4.6 大幅改善了长上下文检索
- 计划更仔细、在更大代码库中更可靠运行
- 代码审查和调试技能提升，能捕捉自己的错误
- **不再需要上下文重置**：Agent SDK 的自动压缩处理上下文增长

**三个 Agent 角色**：

| Agent | 职责 | 解决的问题 |
|-------|------|-----------|
| **规划器 (Planner)** | 将 1-4 句简单提示扩展为完整产品规范；雄心勃勃地确定范围；专注于产品上下文和高层技术设计而非详细技术实现；寻找将 AI 功能融入产品规范的机会 | 之前需要用户提供详细规范 upfront |
| **生成器 (Generator)** | 以 Sprint 方式工作，从规范中逐个选取功能；每个 Sprint 用 React + Vite + FastAPI + SQLite/PostgreSQL 实现；Sprint 结束时自我评估；使用 git 版本控制 | 范围管理、实现质量 |
| **评估器 (Evaluator)** | 使用 Playwright MCP 像用户一样点击运行中的应用；测试 UI 功能、API 端点、数据库状态；按标准评分；任何标准低于硬阈值则 Sprint 失败 | 发现真实 bug、质量保证 |

**关键设计决策**：

1. **规划器不指定细粒度技术细节**
   - 担心：如果规划器 upfront 指定细粒度技术细节但出错，错误会级联到下游实现
   - 策略：约束可交付成果，让 Agent 在工作时找出路径

2. **Sprint 合约机制**
   - 每个 Sprint 前，生成器和评估器协商"完成标准"
   - 原因：产品规范故意高层级，需要弥合用户故事与可测试实现之间的差距
   - 流程：
     1. 生成器提议要构建什么 + 如何验证成功
     2. 评估器审核确保生成器构建正确的东西
     3. 两者迭代直到达成一致
   - 通信通过文件：一个 Agent 写文件，另一个读并响应

### 4.3 运行 Harness：复古游戏制作器

**提示**：
> 创建一个 2D 复古游戏制作器，功能包括关卡编辑器、精灵编辑器、实体行为和可玩测试模式。

**对比实验**：

| Harness 类型 | 时长 | 成本 |
|-------------|------|------|
| 单 Agent | 20 分钟 | $9 |
| 完整 Harness | 6 小时 | $200 |

**成本效益**：Harness 贵 20 多倍，但输出质量差异立即可见。

#### 单 Agent 输出问题

**预期**：可以构建关卡和组件（精灵、实体、瓦片布局），然后点击播放实际玩关卡。

**实际体验**：
- 布局浪费空间，固定高度面板留下大部分视口空白
- 工作流程僵化：尝试填充关卡时提示先创建精灵和实体，但 UI 没有引导用户走向该顺序
- **核心功能损坏**：实体出现在屏幕上但没有任何响应输入
- 代码问题：实体定义与游戏运行时之间的连接损坏，没有表面指示哪里出错

#### 完整 Harness 输出

**规划器扩展**：将一句话提示扩展为 16 功能规范，分布在 10 个 Sprint 中：
- 核心编辑器和播放模式
- 精灵动画系统
- 行为模板
- 音效和音乐
- AI 辅助精灵生成器和关卡设计师
- 游戏导出与可分享链接

**设计系统**：规划器读取前端设计技能，创建视觉设计语言作为规范的一部分。

**Sprint 合约**：每个 Sprint，生成器和评估器协商定义具体实现细节和可测试行为的合约。

**实际体验**：
- 画布使用完整视口，面板大小合理
- 界面有一致的视觉身份，追踪规范中的设计方向
- 某些笨拙仍然存在（工作流程仍不清楚应该先构建精灵和实体），这似乎是基础模型产品直觉的差距

**编辑器对比**：
- 精灵编辑器更丰富、功能更完整
- 更干净的工具调色板、更好的颜色选择器、更可用的缩放控制
- 内置 Claude 集成，可通过提示生成游戏不同部分

**游戏模式对比**：
- **核心差异**：实际能够移动实体并玩游戏
- 物理有些粗糙（角色跳到平台上但重叠），但核心功能工作
- 单 Agent 版本核心功能完全损坏

**评估器发现的问题示例**：

| 合约标准 | 评估器发现 |
|---------|-----------|
| 矩形填充工具允许点击拖动用选定瓦片填充矩形区域 | **失败** — 工具只在拖动起点/终点放置瓦片，而非填充区域。`fillRectangle` 函数存在但未在 mouseUp 时正确触发 |
| 用户可以选择并删除已放置的实体生成点 | **失败** — `LevelEditor.tsx:892` 的 Delete 键处理程序要求同时设置 `selection` 和 `selectedEntityId`，但点击实体只设置 `selectedEntityId`。条件应为 `selection \|\| (selectedEntityId && activeLayer === 'entity')` |
| 用户可以通过 API 重新排序动画帧 | **失败** — `PUT /frames/reorder` 路由定义在 `/{frame_id}` 路由之后。FastAPI 将 'reorder' 匹配为 frame_id 整数，返回 422："unable to parse string as an integer" |

**评估器调校挑战**：
- 开箱即用的 Claude 是糟糕的 QA Agent
- 早期运行中，评估器识别出合法问题，然后说服自己决定它们不是大问题并批准工作
- 倾向于表面测试而非探测边缘情况，更微妙的 bug 经常溜走
- 调校循环：阅读评估器日志 → 找到判断与作者分歧的例子 → 更新 QA 提示解决这些问题
- 经过几轮开发循环，评估器才以作者认为合理的方式评分

**局限性**：
- 小布局问题
- 某些地方交互感觉不直观
- 评估器未充分测试的深层嵌套功能中未发现 bug
- 相比单 Agent 版本（核心功能完全不工作），提升明显

### 4.4 迭代优化 Harness

#### 优化动机

第一版 Harness 结果令人鼓舞，但也笨重、缓慢、昂贵。下一步是找到简化 Harness 而不降低性能的方法。

**核心原则**：Harness 中的每个组件都编码了对模型自身无法做什么的假设，这些假设值得压力测试——因为它们可能不正确，也可能随着模型改进迅速过时。

**模型升级**：Opus 4.6 发布
- 计划更仔细
- 在更大代码库中更可靠运行
- 代码审查和调试技能提升
- 长上下文检索大幅改善
- 这些都是 Harness 原本要补充的能力

#### 激进简化尝试

首次尝试大幅削减 Harness 并尝试一些创意新想法，但无法复制原始性能。也很难判断 Harness 设计的哪些部分实际上是承载负载的，以及以什么方式。

#### 系统化简化方法

基于经验，转向更系统的方法：一次移除一个组件，审查对最终结果的影响。

#### 移除 Sprint 结构

**假设**：Sprint 结构帮助将工作分解为模型可以连贯处理的块。鉴于 Opus 4.6 的改进，有理由相信模型可以原生处理这项工作，无需这种分解。

**保留组件**：
- **规划器**：仍然增加明显价值。没有规划器，生成器会低估范围：给定原始提示就开始构建，没有先规范工作，最终创建的功能丰富的应用不如规划器版本。
- **评估器**：仍然增加价值

**变更**：
- 完全移除 Sprint 结构
- 将评估器移到运行结束时的单次通过，而非每个 Sprint 评分
- 模型能力改变评估器的负载程度：
  - 4.5 时代：构建处于生成器独立做得好能力的边缘，评估器在整个构建中捕获有意义的问题
  - 4.6 时代：模型原始能力增加，边界向外移动。原本需要评估器检查才能连贯实现的任务，现在通常在生成器独立处理良好的范围内，对于这些任务，评估器成为不必要的开销。但对于仍处于生成器能力边缘的构建部分，评估器继续提供真正的提升。

**实践含义**：评估器不是固定的 yes/no 决策。当任务处于当前模型可靠独立完成的范围之外时，它值得成本。

**新增功能**：改进 AI 功能构建方式的提示，特别是让生成器构建能够通过工具驱动应用自身功能的 proper agent。

#### 更新后 Harness 的结果：数字音频工作站 (DAW)

**提示**：
> 使用 Web Audio API 在浏览器中构建一个功能完整的 DAW。

**成本**：约 4 小时，$124 token 成本

**时间分配**：

| Agent & 阶段 | 时长 | 成本 |
|-------------|------|------|
| 规划器 | 4.7 分钟 | $0.46 |
| 构建 (第 1 轮) | 2 小时 7 分钟 | $71.08 |
| QA (第 1 轮) | 8.8 分钟 | $3.24 |
| 构建 (第 2 轮) | 1 小时 2 分钟 | $36.89 |
| QA (第 2 轮) | 6.8 分钟 | $3.09 |
| 构建 (第 3 轮) | 10.9 分钟 | $5.88 |
| QA (第 3 轮) | 9.6 分钟 | $4.06 |
| **总计 V2 Harness** | **3 小时 50 分钟** | **$124.70** |

**观察**：
- 大部分时间用于构建器，连续运行超过两小时，无需 Opus 4.5 所需的 Sprint 分解
- 规划器将一行提示扩展为完整规范
- 生成器模型在规划应用和 Agent 设计、连接 Agent、在移交给 QA 前测试方面做得很好

**QA 发现的真实差距**：

**第 1 轮反馈**：
> 这是一个强大的应用，具有出色的设计保真度、可靠的 AI Agent 和良好的后端。主要失败点是功能完整性——虽然应用看起来令人印象深刻且 AI 集成工作良好，但几个核心 DAW 功能只是显示而无交互深度：片段无法在时间线上拖动/移动，没有乐器 UI 面板（合成器旋钮、鼓垫），没有视觉效果编辑器（EQ 曲线、压缩器仪表）。这些不是边缘情况——它们是使 DAW 可用的核心交互，规范明确要求它们。

**第 2 轮反馈**：
> 剩余差距：
> - 音频录制仍然是仅存根（按钮切换但没有麦克风捕获）
> - 片段边缘拖动调整大小和片段分割未实现
> - 效果可视化是数字滑块，不是图形（无 EQ 曲线）

**结论**：
- 生成器在独立工作时仍然容易遗漏细节或存根功能
- QA 在捕捉这些最后一公里问题方面仍然增加价值，供生成器修复
- 最终应用拥有功能音乐制作程序的所有核心部分：工作排列视图、混音器、浏览器中运行的传输
- 能够通过提示组合短歌曲片段：Agent 设置速度和调、铺设旋律、构建鼓轨道、调整混音级别、添加混响
- 歌曲创作的核心原语存在，Agent 可以自主驱动它们，使用工具从头到尾创建简单制作

## 五、未来展望

### 5.1 模型演进趋势

随着模型持续改进，可以大致预期它们能够：
- 工作更长时间
- 处理更复杂的任务

**双重影响**：
1. 在某些情况下，围绕模型的脚手架会随时间变得不那么重要，开发者可以等待下一个模型，看某些问题自行解决
2. 另一方面，模型越好，开发能够实现基线模型无法完成的复杂任务的 Harness 的空间就越大

### 5.2 值得传承的经验教训

1. **实验与调优**
   - 始终针对你构建的模型进行实验
   - 阅读其在真实问题上的 traces
   - 调优性能以实现期望的结果

2. **任务分解与专业化**
   - 在处理更复杂任务时，有时可以通过分解任务并将专业化 Agent 应用于问题的每个方面来获得提升空间

3. **Harness 持续演进**
   - 当新模型发布时，通常最好重新审视 Harness
   - 剥离不再承载性能的部件
   - 添加新部件以实现以前可能无法实现的更大能力

### 5.3 核心信念

作者坚信：**有趣的 Harness 组合空间不会随着模型改进而缩小。相反，它会移动，AI 工程师的有趣工作是不断找到下一个新颖的组合。**

## 六、关键概念与术语

| 术语 | 定义 |
|------|------|
| **Harness** | 用于控制和管理 Agent 的工程体系 |
| **生成器 (Generator)** | 执行实际工作（编码/设计）的 Agent |
| **评估器 (Evaluator)** | 评判生成器产出质量的独立 Agent |
| **规划器 (Planner)** | 将高层提示扩展为详细产品规范的 Agent |
| **上下文焦虑 (Context Anxiety)** | 模型接近上下文限制时提前结束工作的倾向 |
| **上下文重置 (Context Reset)** | 完全清空上下文窗口，启动全新 Agent |
| **压缩 (Compaction)** | 在原地总结早期对话，让同一 Agent 继续 |
| **Sprint 合约** | 生成器与评估器在每个 Sprint 前协商的"完成标准" |
| **GAN 启发** | 生成对抗网络架构（生成器 vs 判别器）的启发 |
| **AI slop** | 高度通用的 AI 生成内容，缺乏原创性 |
| **少样本示例 (Few-shot)** | 提供少量示例来校准模型行为 |

## 八、精读总结

### 8.1 核心创新点

1. **GAN 启发的双/三 Agent 架构**：将生成与评估分离，解决自我评估偏差问题
2. **评估标准具象化**：将主观判断转化为可评分的具体标准
3. **Sprint 合约机制**：在灵活性与质量保证之间找到平衡
4. **上下文管理策略**：根据模型特性选择重置或压缩

### 8.2 对 KuiklyUI 的启示

**直接适用**：
- 生成器-评估器分离架构可用于代码审查
- 评估标准具象化可应用于架构合规性检查
- Sprint 合约机制可集成到 OpenSpec 工作流

**需要适配**：
- 前端设计的具体标准需要转换为 KMP/跨平台开发标准
- Playwright MCP 测试需要替换为 KMP 生态的测试工具
- 成本考量需要平衡（$200 vs $9 的差异对开源项目显著）

**长期思考**：
- Harness 应随模型能力演进持续简化
- 保持"最简可行"原则，避免过度工程
- 关注模型能力边界，在边界处提供脚手架
