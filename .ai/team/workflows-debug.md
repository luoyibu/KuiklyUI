# Bug 跟进工作流

> 供团队成员阅读。当前为**手动版本**，AI 辅助完成大部分工作，人工参与关键节点。
> 无需打开 IDE（Android Studio、Xcode、DevEco Studio）。

**前置依赖**：两个 Skills 已集成到项目，无需额外安装
- `.agents/skills/systematic-debugging/` — 系统性根因分析
- `.agents/skills/kuikly-app-runner/` — KuiklyUI 多平台编译运行

当前兼容 Claude Code、OpenCode、Cursor、CodeBuddy、Claude-internal，[兼容方案详情](../../harness-engineer/HARNESS_OVERVIEW.md#附录-b多工具-skills-兼容)

## Step 1：描述 bug，让 AI 构造复现 Demo

### 你发给 AI 的内容

```
我遇到一个 bug：[简单描述现象，例如：LazyColumn 滚动到底部后加载更多不触发]

平台：[iOS / Android / HarmonyOS]
页面/场景：[描述在哪个功能、哪个页面]
复现步骤：
1. [步骤 1]
2. [步骤 2]
3. ...
预期行为：[应该发生什么]
实际行为：[实际发生了什么]

请先帮我构造一个可以复现这个 bug 的最小 Demo，放到 demo/ 目录下。
注意：这一步只需要构造 Demo 并让它编译通过，不需要分析 bug 原因。
编译通过后，通过 kuikly-app-runner skill 在我的 [iOS 模拟器/Android 模拟器/真机] 上跑起来，
告诉我怎么操作来触发这个 bug。
```

> 如果你已经有复现 Demo（或者能提供一段代码），可以直接附上，让 AI 帮你移植到当前工程：
> ```
> 我有一段可以复现的代码，帮我把它移植到 demo/ 目录下，编译通过后跑起来：
> [粘贴你的代码]
> ```

### AI 会做的事

1. 在 `demo/src/commonMain/.../pages/debug/` 下创建 `BugRepro{功能名}Page.kt`
2. 根据你描述的场景构造最小复现代码（选择合适的 DSL：自研 DSL 或 Compose DSL）
3. 调用 `kuikly-app-runner` 编译并部署到模拟器/真机
4. 告诉你：用什么操作来触发 bug

---

## Step 2：确认能否复现

在设备/模拟器上按 AI 说的操作步骤操作。

**如果复现成功，回复：**
```
我刚才已经复现了这个 bug，可以稳定复现。
```

**如果无法复现，回复：**
```
我没能复现，[描述你做了什么，看到了什么]。
请调整 Demo 或操作步骤。
```

> AI 会根据你的反馈调整 Demo，重新编译部署，直到 Demo 能稳定复现。

---

## Step 3：开始分析，添加诊断日志

复现成功后，让 AI 开始系统性分析：

### 你发给 AI 的内容

```
我已经可以稳定复现了。

接下来请用 systematic-debugging skill 来详细分析这个 bug 的可能原因。
请在关键节点添加 KLog 诊断日志，覆盖你猜测的每个假设点，
然后重新把 App 跑起来，告诉我怎么操作，我会再次复现，
然后你基于日志来确认是否符合你猜测的 bug 原因。
```

### AI 会做的事

1. 用 `systematic-debugging` 方法论分析相关代码
2. 列出 2-3 个按优先级排列的可能原因
3. 在 Demo 的关键位置添加 `KLog.d(TAG, "...")` 诊断日志，每个假设都有对应的日志覆盖
4. 重新编译部署
5. 告诉你：操作步骤，以及复现后重点看哪些日志输出

---

## Step 4：再次操作复现

按 AI 说的步骤再次操作，触发 bug。

**操作完成后，回复：**
```
操作完成了，请查看日志分析。
```

---

## Step 5：AI 分析日志（可能循环多次）

AI 会读取 `./logs/` 下的日志，对照各假设进行分析，给出结论。

### AI 给出结论后，你需要判断

**如果分析合理，根因明确：**
```
根因分析合理，我认同这个结论。请给出修复方案。
```

**如果分析不确定，需要更多日志：**
```
这个分析还不够确定，[说明你的疑问]。
请在 [某个位置] 添加更多日志，重新跑一次。
```

**如果分析方向感觉不对：**
```
我觉得问题可能不在这里，[说明你的判断]。
请重新分析，看看是否是 [你怀疑的方向] 的问题。
```

> **给读者的提示**：复杂 bug，AI 不一定能一次找到根因，这很正常。
> 你需要结合自己对业务和代码的理解来判断 AI 的分析方向是否正确。
> 如果 AI 多次猜测仍然无法确认，很可能是当前日志不够充分——
> 明确告诉 AI 在哪些位置添加更多日志，往往比让 AI 继续猜更有效。

这一步可能会循环多次：AI 补充日志 → 你操作复现 → AI 分析日志 → 直到根因确认。

---

## Step 6：确认根因，让 AI 给出修复方案

根因确认后：

### 你发给 AI 的内容

```
根因分析确认了，我认同你的结论。
请给出修复方案，说明你打算修改哪些地方、为什么这样修改。
方案确认后再动手实施。
```

### AI 会做的事

给出修复方案，包含：
- 需要修改的文件和位置
- 修改的具体内容
- 为什么这样修改能解决问题

**你确认方案后回复：**
```
方案 OK，请实施修复。
```

**如果需要调整：**
```
方案有个问题：[说明你的疑虑]。请重新考虑 [某个点]。
```

---

## Step 7：Review 并合入

AI 实施修复后会提交代码并通过工蜂发起 MR。

**你需要做的：**
1. 在工蜂上 Review 修复代码，确认改动合理
2. 确认无问题后合入 MR

**如果需要修改：**
```
Review 发现一个问题：[描述问题]，请修改。
```
