## 文章开头

我在采用任何有意义的工具时，都必须经历三个阶段：(1) 低效期 (2)  adequacy 期，最后 (3) 工作流程和生活发生改变的发现期。

在大多数情况下，我必须强迫自己度过第1和第2阶段，因为我通常已经有一个令我满意且舒适的工作流程。采用新工具感觉像是一项工作，我*不想*付出努力，但我通常会这样做，为了成为我这个手艺的全面人才。

这是我的旅程，讲述了我如何在AI工具中找到价值，以及我接下来要尝试什么。在一片过于戏剧化、炒作的观点海洋中，我希望这代表了一种更细致、更平衡的方法来看待我对AI的观点以及它们如何随时间变化。

这篇博客文章完全是我亲手写的，用我自己的话。我讨厌我必须这样说，但特别是考虑到主题，我想明确说明这一点。

---

## 步骤1：放弃聊天机器人

立即停止使用聊天机器人（例如ChatGPT、网页版Gemini等）进行有意义的工作。聊天机器人具有真正的价值，是我AI工作流程的日常组成部分，但它们在编码方面的效用非常有限，因为你主要是希望它们基于先前的训练得出正确的结果，而纠正它们需要一个人（你）反复告诉它们错了。这效率低下。

我认为每个人对AI的第一次体验都是聊天界面。而且我认为每个人尝试用AI编码的第一次体验都是要求聊天界面写代码。

在我还是一个重度AI怀疑论者的时候，我的第一个"哇哦"时刻是将Zed的命令面板的截图粘贴到Gemini中，要求它用SwiftUI重现它，并且真的惊讶于它做得*非常好*。今天Ghostty在macOS上发布的命令面板只是对我几秒钟内Gemini为我生成的内容进行了非常轻微的修改。

但当我尝试为其他任务重现这种行为时，我感到失望。在 brownfield 项目的背景下，我发现聊天界面经常产生糟糕的结果，我发现自己在界面之间复制粘贴代码和命令输出感到非常沮丧。这显然比我自己做工作要低效得多。

要找到价值，你*必须*使用**智能体（agent）**。智能体是行业采用的术语，指能够聊天并在循环中调用外部行为的LLM。至少，智能体必须具有的能力是：读取文件、执行程序、发出HTTP请求。

## 步骤2：复现你自己的工作

我旅程的下一个阶段尝试了Claude Code。我直说吧：我最初并不印象深刻。我只是没有从我的会话中获得好的结果。我觉得我必须润色它产生的所有内容，这个过程比我自己做要花更多时间。我读了博客文章，看了视频，但就是不太印象深刻。

没有放弃，我**强迫自己用智能体复现所有手动提交。**我字面意义上做了两次工作。我会手动做工作，然后我会努力让智能体产生质量和功能上相同的结果（当然不让它看到我的手动的解决方案）。

这*非常痛苦*，因为它妨碍了简单地完成工作。但我在非AI工具方面有足够的经验，知道摩擦是自然的，我不能在不耗尽努力的情况下得出坚定、可辩护的结论。

但是，专业知识形成了。我很快从第一性原则为自己发现了其他人已经在说的东西，但自己发现它让我有了更扎实的基本理解。

1. 将会话分解为单独的清晰、可操作的任务。不要试图在一个大型会话中"画猫头鹰"。
2. 对于模糊的请求，将工作分成单独的规划与执行会话。
3. 如果你给智能体一种验证其工作的方式，它更经常地会自己修复错误并防止回归。

更一般地说，我还发现了智能体——在当时——擅长什么的边界，不擅长什么，以及对于它们擅长的任务如何获得我想要的结果。

所有这些都带来了显著的效率提升，以至于我开始自然地使用智能体，感觉不比自己做的慢（但我仍然不觉得更快，因为我主要是在照看智能体）。

这里值得重申的负面空间是：这里效率提升的一部分是理解什么时候*不*要使用智能体。在智能体可能失败的事情上使用智能体显然是巨大的时间浪费，拥有完全避免这种情况的知识可以节省时间。

在这个阶段，我发现智能体有足够的价值，我很乐意在我的工作流程中使用它们，但仍然不觉得我看到了任何净效率提升。我不在乎，在这一点上我对AI作为工具感到满意。

## 步骤3：日终智能体

为了尝试找到一些效率，我接下来开始了一个新模式：**每天最后30分钟留出时间来启动一个或多个智能体。**我的假设是，*也许*如果智能体在我无法工作的时间里取得一些*积极进展*，我可以获得一些效率。基本上：不是试图在我有的时间里做更多，而是试图在我没有的时间里做更多。

与之前的任务类似，我一开始发现这既不成功又烦人。但是，我再一次很快发现了真正有帮助的不同类别的工作：

- **深度研究会话**，我会要求智能体调查某个领域，例如找到特定语言中具有特定许可证类型的所有库，并为每个库生成多页摘要，说明其优缺点、开发活动、社会情绪等。
- **并行智能体尝试我没有时间开始的不同模糊想法。**我不期望它们在这里产生我会发布的东西，但也许可以在第二天我处理任务时揭示一些未知的未知。
- **问题和PR分类/审查。**智能体擅长使用`gh`（GitHub CLI），所以我手动编写了一个快速方法来并行启动一堆来分类问题。我不会允许智能体回应，我只是想要第二天的报告，试图引导我走向高价值或低努力的任务。

要明确的是，我没有像其他人那样走得那么远，让智能体整夜在循环中运行。在大多数情况下，智能体在不到半小时内完成了任务。但是，工作日的后段时间，我通常很累，刚从心流状态中出来，发现自己个人效率太低，所以将我的努力转移到启动这些智能体上，我发现给了我第二天早上一个"热启动"，让我比原本更快地开始工作。

我很开心，我开始觉得我在AI之前做得更多，即使只是稍微多一点。

## 步骤4：外包稳操胜券的任务

到这一点，我对我的AI擅长什么、不擅长什么非常有信心。我对某些任务有很高的信心，AI会实现一个基本正确的解决方案。所以我旅程的下一步是：**让智能体做所有这些工作，而我做其他任务。**

更具体地说，我会每天开始，取前一天晚上分类智能体的结果，手动过滤以找到智能体几乎肯定能很好解决的问题，然后让它们在后台继续运行（一次一个，不是并行）。

与此同时，**我做其他事情。**我不是去社交媒体（没有AI时比平时更多），我不是看视频，等等。我处于自己正常的、AI之前的深度思考模式，处理我想处理或必须处理的事情。

**在这个阶段非常重要：关闭智能体桌面通知。**上下文切换非常昂贵。为了保持效率，我发现作为人类，我的工作是在我打断智能体时保持控制，而不是反过来。不要让智能体通知你。在我工作的自然休息期间，切换过去检查它，然后继续。

重要的是，我认为"做其他事情"有助于抵消广受关注的Anthropic技能形成论文。嗯，你在做权衡：不形成你委托给智能体的任务的技能，同时在你继续手动处理的任务中自然地继续形成技能。

在这一点上，我坚定地处于"不可能回去"的领域。我感觉更有效率，但即使我没有，我最喜欢的是我现在可以将我的编码和思考集中在我真正喜欢的任务上，同时仍然充分地完成我不喜欢的任务。

---

## 步骤5：构建Harness（工程化约束体系）

冒着陈述显而易见的风险：当智能体第一次就产生正确的结果时，或者最坏的情况下产生需要最少润色的结果时，它们效率要高得多。实现这一点的最可靠方法是给智能体快速、高质量的工具来自动告诉它什么时候错了。

我不知道这是否有一个广泛的行业接受的术语，但我逐渐称之为"harness engineering（约束工程）"。它的理念是，每当你发现智能体犯了错误，你就花时间设计一个解决方案，使智能体永远不会再犯同样的错误。我不需要在这里发明任何新术语；如果另一个存在，我会加入这个潮流。

这有两种形式：

1. **更好的隐式提示（AGENTS.md）。**对于简单的事情，比如智能体反复运行错误的命令或找到错误的API，更新`AGENTS.md`（或等效文件）。这里有一个来自Ghostty的例子：https://github.com/ghostty-org/ghostty/blob/ca07f8c3f775fe437d46722db80a755c2b6e6399/src/inspector/AGENTS.md。该文件中的每一行都是基于一个糟糕的智能体行为，它几乎完全解决了它们所有。

2. **实际的、编程的工具。**例如，截图脚本、运行过滤测试等。这通常伴随着AGENTS.md的更改，让它知道这些工具的存在。

**这就是我今天所处的位置。**每当我看到智能体做了一件坏事，我都会认真努力防止它再次做那件坏事。或者相反，我正在认真努力让智能体能够验证它们正在做一件好事。

---

## 步骤6：始终保持智能体运行

与第5步同时进行，我也在以**始终保持智能体运行**的目标运作。如果没有智能体在运行，我会问自己"现在有什么智能体可以为我做的事情吗？"

我特别喜欢将其与更慢、更深思熟虑的模型结合，如Amp的deep mode（基本上就是GPT-5.2-Codex），它可能需要30多分钟来进行小的更改。另一方面，它确实倾向于产生非常好的结果。

**我还[没有？]运行多个智能体，目前真的不想。**我发现让一个智能体运行对我来说是一个很好的平衡，介于能够做我享受的深度手动工作，和照看我的那种愚蠢但神秘地富有成效的机器人朋友之间。

"始终保持智能体运行"的目标仍然只是一个目标。我想说现在我可能在一个正常工作日中有效地让后台智能体运行10%到20%的时间。但是，我正在积极努力改进这一点。

**我不想为了运行智能体而运行智能体。**我只想在有一个我认为真正对我有帮助的任务时才运行它们。这个目标的部分挑战是改进我自己的工作流程和工具，这样我就可以有源源不断的我可以委托的高质量工作。即使没有AI，这也很重要！

## 今天

这就是我今天所处的位置。

通过这段旅程，我个人已经达到了一个点，在现代AI工具方面取得了成功，我相信我以扎根于现实的适当平衡的观点来对待它。我真的不在乎AI是否会留下来，我是一个软件工匠，只是为了热爱而建造东西。

整个领域发展如此迅速，我相信我会很快回顾这篇文章并嘲笑我的天真。但是，正如他们所说，如果你不能为你的过去自己感到尴尬，你可能没有在成长。我只希望我朝着正确的方向成长！

我在这里没有任何利益关系，当然除了实用性之外，还有其他原因避免使用AI。我完全尊重任何人对此的个人决定。我不是来说服你的！对于那些感兴趣的人，我只是想分享我个人驾驭这些新工具的方法，并一瞥我*一般*如何处理新工具，无论是否与AI有关。

```markdown
# Inspector Subsystem

The inspector is a feature of Ghostty that works similar to a
browser's developer tools. It allows the user to inspect and modify the
terminal state.

- See the full C API by finding `dcimgui.h` in the `.zig-cache` folder
  in the root: `find . -type f -name dcimgui.h`. Use the newest version.
- See full examples of how to use every widget by loading this file:
  <https://raw.githubusercontent.com/ocornut/imgui/refs/heads/master/imgui_demo.cpp>
- On macOS, run builds with `-Demit-macos-app=false` to verify API usage.
- There are no unit tests in this package.
```
